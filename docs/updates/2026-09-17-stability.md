# Обновление 17.09.2026: сессии, CMS и проверки

Ветка: `feat/catalog-core`. Существующие записи страниц, игр, секций,
изображений и пользователей не пересоздаются.

## Что изменено

- Сервер использует refresh token при истечении access token и записывает
  обновлённые cookies. Временный сбой авторизации не удаляет refresh cookie.
- Выход пытается отозвать текущую сессию Supabase и очищает cookies.
- Admin API проверяет полномочия каталога или контента поверх RLS.
- Защищённые страницы получают private/no-store. API возвращает 401/403
  при отсутствии сессии или разрешения.
- CTA-ссылки проверяются при записи и чтении блоков.
- Все десять типов блоков имеют русские названия и корректные стартовые
  шаблоны, общие для редактора страниц и редактора игр.
- Добавлено отображение блоков подборки игр и FAQ. Пустой список ID выбирает
  до 24 публичных записей, непустой — указанные записи в заданном порядке.
  FAQ использует опубликованные faq_entries и выводит текст без выполнения HTML.
  Полноценный редактор FAQ в этот пакет не входит.
- Изменение страницы сохраняет первоначальную дату публикации.
- Сохранение/удаление секции и изменение медиа проверяют наличие изменённой
  записи вместо ложного сообщения об успехе.
- Убраны неиспользуемые импорты, исправлен mobile navigation smoke test.
- GitHub Actions проверяет типы, unit-тесты и сборку. Отдельная PostgreSQL
  fixture проверяет миграцию разрешений и сохранение администратора.

## Обновление на Windows

Остановить dev-сервер через Ctrl+C, затем в каталоге проекта:

```powershell
git status --short
git checkout feat/catalog-core
git pull --ff-only origin feat/catalog-core
npm.cmd install
npm.cmd run verify
npm.cmd run dev
```

Существующий .env с подключением к вашей Supabase оставить.
Если git сообщает о конфликте, не выполнять reset/clean: сначала разобрать
локальные изменения. Git-команды и npm не применяют SQL к Supabase.

## Единственная новая миграция

В SQL Editor своего проекта Supabase выполнить содержимое:

`supabase/migrations/202609170001_profile_update_permissions.sql`

Она отзывает UPDATE всей таблицы/защищённых столбцов profiles у клиентских
ролей и оставляет UPDATE display_name/avatar_url. Текущее значение роли
администратора не изменяется. Прежняя RLS self-update остаётся активной.

Затем выполнить `supabase/tests/profile_permissions.sql`: успешный результат
без исключения подтверждает ожидаемые grants. Скрипт не меняет данные.

Не выполнять заново старые миграции, seed или файлы из tests/fixtures:
fixtures предназначены только для пустой временной БД GitHub Actions.
Рабочую Supabase из GitHub Actions мы не подключаем.

## Ручная проверка

1. Войти прежним администратором, открыть страницу и игру в админке.
2. Убедиться, что прежние блоки, изображения и порядок сохранились.
3. Изменить текст существующего блока, сохранить и проверить публичную страницу.
4. Проверить русские названия типов в обоих редакторах.
5. Проверить подборку игр. Для FAQ нужны опубликованные записи faq_entries.
6. Для проверки refresh удалить только sb-access-token в DevTools → Application
   → Cookies, оставив sb-refresh-token, затем открыть /admin:
   вход должен сохраниться и access cookie появиться снова.
7. Выйти и убедиться, что /admin снова требует входа.

Браузерный smoke-тест запускается отдельно с вашим .env:

```powershell
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

CI использует фиктивные публичные переменные для сборки и моки для unit-тестов.
Он не подтверждает состояние production Supabase или внешний Cloudflare deploy.
